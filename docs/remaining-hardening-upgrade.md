# 后续批次升级与数据核对

代码修复对应问题 3、5、6、9、12、14、15、16、20、21。以下是部署步骤，本次开发没有对现有服务执行这些操作。

## 数据库和客户端

先备份数据库及客户端离线数据，再停止旧后端写入并升级。Docker 文件卷按 [旧数据升级](runtime-data-upgrade.md) 处理，桌面来源按 [桌面升级](desktop-origin-upgrade.md) 处理。

PostgreSQL 继续通过 `python backend/run_migrations.py` 管理结构，当前头版本为 `20260925_28`。SQLite 桌面启动使用兼容的轻量迁移。新增三步：

- `26`：计时客户端 ID、来源时区标记及唯一索引。历史记录默认 `legacy`，不自动改变时间。
- `27`：重复复习计划先留审计快照，再合并并建唯一索引。取最新复习状态、最大 repetitions，保留任一旧行的归档标记。**该合并不可逆，拒绝 downgrade；需要回退时恢复升级前数据库备份。**
- `28`：聊天轮次标识、进度状态及每轮用户/助手消息唯一索引。历史消息默认已完成；新流按短事务保存进度。

前后端要一起更新。章节、错题、Anki 复习新增必填 UUID `attempt_id`；相同答案的重试必须复用它。Anki 离线评分还携带原始复习时间及期望服务器版本，更新过的服务器会公布 `review_attempts` 能力。迁移期间保留本机离线队列，不能清理 IndexedDB 或 LocalStorage 来“重置同步”。

若待同步评分与另一设备的新进度冲突，账户菜单提供两种明确处理方式：采用云端，或按当前时间重新提交该评分。前者放弃本机待确认评分；后者产生新的复习尝试，不覆盖旧请求。云端已删卡片时不会自动重新创建或伪造复习。

## 历史番茄钟时间

`created_at` 是入库时间，不能当作开始/结束时间一起平移。旧在线代码使用过服务器本地时间，旧离线导入可能已经使用 UTC。不能仅凭用户名或记录日期判断来源。

1. 从部署配置、旧日志和可核对的用户记录确认来源，在数据库备份上分组列出 ID。ID 文件格式例如 `[12, 18, 27]`。
2. 从 backend 目录、使用已配置好的目标数据库环境生成计划，默认只读取，不修改数据库：

   ```bash
   PYTHONPATH=. python scripts/repair_pomodoro_times.py --ids /secure-backup/local-time-ids.json --source-zone Asia/Shanghai --plan /secure-backup/local-time-plan.json
   ```

3. 核对计划内的用户、记录 ID、转换前后时间和学习事件。对已经是 UTC 的旧记录，另建 ID 文件并指定 `--source-zone UTC`，只确认其来源标记。`mixed` 表示旧开始时间与新 UTC 结束时间混用，脚本只转换开始时间。
4. 停止写入及后台投影任务，再对**已核对的同一计划**执行：

   ```bash
   PYTHONPATH=. python scripts/repair_pomodoro_times.py --plan /secure-backup/local-time-plan.json --apply
   ```

脚本在同一事务中转换计时、相关学习事件、证据及 outbox 时间，重算受影响的概念状态。记录或事件自预览后有变化则中止；已完成的计划重复执行不再平移。夏令时歧义时间拒绝自动转换，应先逐条确认。计划含用户数据，保存在备份目录，不提交 Git。

## 浏览器旧缓存与失败恢复

新计时缓存按用户 ID 和账户创建时间保存。旧 `pomodoro-storage`、`mnemox_pomodoro_focus_tasks`、`mnemox_pomodoro_task_sets` 没有可信归属，升级不会自动认领或删除。先在确认属于原使用者的浏览器/桌面来源中导出这些原始 JSON，再和云端记录核对；已存在的后端计时不能重新当作独立离线记录导入。来源无法确认时继续保留备份。

新的未同步计时不再被 500 条历史缓存上限裁掉；待确认记录保留并显示同步错误。发生 409 时先核对云端已有终态，不生成新 ID 强行重复上传。

聊天只有完成消息落库后才发送完成标记。关闭窗口或后端退出后，重新打开历史可读取已提交内容；`streaming` 或 `interrupted` 都显示“回复未完成”。这是保留进度，不是断点续调供应商模型。

资料更新时索引失败，正文已保存，投影保持待更新或失败状态；启动恢复流程或资料重新索引可重试。重建前关键词检索仍可用，旧向量不会被当作当前正文返回。

## 验收

- 两个账号分别计时、重启、切换，检查历史和背景不串号；断网停止后重试，云端仍只有一条中断记录。
- 重复提交同一个复习 UUID，检查 repetitions、熟练度和 `review.completed` 只增加一次。
- 聊天收到一段后停止或断开，再刷新历史，检查输入及已收到内容存在、状态未完成。
- 更新资料后人为阻断索引，确认旧文本不再作为语义证据返回。
- Anki 断网创建并评分、关闭重开、联网同步，检查只创建一张卡并应用一次评分；超过 200 张卡与错题可以完整读取。

可重复的 PostgreSQL 验收在 `backend/tests/test_hardening_postgres.py`。它只接受显式配置的回环地址、专用用户及名为 `hardening_test` 的**空临时数据库**；无配置时跳过，不能指向正式数据库。
