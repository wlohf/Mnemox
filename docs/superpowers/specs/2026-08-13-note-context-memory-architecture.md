## 1. 决策摘要

笔记与长期记忆可以互相提供证据，但不能合并成同一类数据。Mnemox 将笔记定义为用户显式创建或导入的知识内容，将记忆定义为对用户目标、偏好、困惑和阶段变化的可审核声明，将学习者状态定义为由练习、回忆和复习等证据计算出的派生状态。

笔记采用三层**逻辑**存储，而不是强制部署三套数据库：

1. **原始笔记层**：SQL `notes` 保存 Markdown 正文、标题、标签、归属、关联和更新时间，是 Mnemox 内部的规范来源。
2. **检索投影层**：`ContextStore` 保存或即时生成 chunk、摘要、关键词/稀疏索引、向量和检索元数据；必须可从原始笔记重建。
3. **派生理解层**：概念关联、记忆候选和学习证据引用只保存带来源的派生结论；不能覆盖原始笔记，也不能成为唯一事实来源。

笔记检索采用三阶段查询：

1. **路由与范围过滤**：先限定用户、项目、资料、标签、时间和授权范围。
2. **混合召回**：组合标题/标签、Sparse/BM25 精确召回与 Dense 语义召回；无 embedding 时保留关键词降级。
3. **重排与分层加载**：融合后可选 reranker，再按 L0 标题/摘要、L1 相关摘录、L2 全文逐级加载。

这份决策细化四层学习智能中的 `ContextStore`、概念图谱、时态记忆和学习者模型边界，不新增与四层并列的“第五层”。

## 2. 为什么笔记不等于记忆

| 内容 | 归属 | 原因 |
| --- | --- | --- |
| “BM25 根据词频和文档频率计算相关性” | 原始笔记 / ContextStore / 概念图谱候选 | 这是知识内容，不是用户状态 |
| “我理解公式时更喜欢先看案例” | 记忆候选 | 这是可能长期影响交互的用户偏好 |
| “我今天做 BM25 练习只答对 40%” | 学习事件 / `learner_evidence` | 这是带时间的直接学习证据 |
| “我已经掌握 BM25” | 笔记原文；最多成为低可靠度自评候选 | 自述不能替代答题、回忆、解释和复习证据 |
| “下个月重点学习混合检索” | 目标或时态记忆候选 | 这是有有效期的计划状态 |

整篇笔记不得直接复制为长期记忆。只有同时满足以下条件的片段才可生成记忆候选：

- 描述用户本人，而不是普通领域知识；
- 未来可能影响解释、排序、提醒或计划；
- 能回链到 `note_id`、版本/更新时间和原文证据；
- 具有置信度、审核状态和失效/删除语义；
- 未确认候选不得作为稳定偏好静默影响高风险决策。

笔记提到某个概念，只能建立 `note -> concept` 的来源关系。除非伴随练习、回忆、解释、应用或人工修正证据，否则不得直接提高 `user_concept_state.mastery_estimate`。

## 3. 三层逻辑存储

### 3.1 原始笔记层

当前规范来源是 SQL `notes`：

```text
note_id / user_id
title / markdown_content / tags / note_type
material_id / chapter_id / note_links
source_path（外部来源指针）
created_at / updated_at
```

后续需要补充稳定来源标识和内容版本，但不能通过向量 ID 或文件路径代替 `note_id + user_id` 的领域身份。Obsidian 导入/同步必须明确文件所有权、vault/file 稳定 ID 和冲突策略；在写回协议完成前，不把检索投影当作 Obsidian 文件的所有者。

### 3.2 检索投影层

`ContextStore` 的笔记投影至少携带：

```text
user_id / namespace
source_type=note / source_id=note_id
source_version / chunk_id
title / tags / excerpt
index_mode / embedding_model / index_version
created_at / refreshed_at
```

投影可以由 SQL 关键词查询、Chroma 或未来通过 Spike 的 Qdrant 实现。业务层只依赖 `ContextStore.ingest/retrieve/load_tiered/forget`，不得依赖某个向量数据库的专有类型。

### 3.3 派生理解层

同一篇笔记可以产生三类彼此隔离的派生数据：

- **概念关系**：笔记解释、举例或关联了哪些概念，保存来源片段、模型版本、置信度和审核状态。
- **记忆候选**：仅提取与用户本人有关且未来有用的声明，默认进入 staged/待审核状态。
- **学习证据引用**：只有符合学习者模型证据契约的行为或人工修正才能写入；笔记正文自身通常不是直接掌握证据。

删除笔记时，所有派生数据必须按来源删除、失效或解除关联；已由用户独立确认的记忆声明是否保留，必须通过明确策略决定，不能静默悬空。

## 4. 三阶段检索

### 4.1 路由与范围过滤

查询先确定是否需要笔记，并限制：

- `current_user.id`；
- 当前项目、资料或目标范围；
- 标签、笔记类型、时间和授权；
- 是否允许使用待审核记忆。

用户隔离必须由数据访问层和 `ContextStore` 双重保证，不能只靠 Prompt 或调用方约定。

### 4.2 混合召回

目标召回组合为：

```text
标题/标签/结构过滤
  + Sparse/BM25（精确术语、缩写、产品名）
  + Dense（同义表达、语义相关）
  -> 融合（例如 RRF）
```

第一条纵向切片仍可使用现有关键词实现；是否引入 Qdrant 必须在同一质量集上比较后决定。没有 embedding Key 或向量服务失败时，关键词检索继续工作并返回明确的降级状态。

### 4.3 重排与分层加载

召回结果先去重、融合和可选 rerank，再按 token 预算加载：

- L0：标题、一行摘要和来源元数据；
- L1：命中位置附近的相关摘录；
- L2：确认需要时加载完整笔记或更大上下文窗口。

回答必须携带 `note_id`、标题、命中片段和检索模式，避免只返回模型重述而无法回看原文。

## 5. 写入、更新与删除生命周期

目标写入路径：

```text
创建/修改笔记
  -> 同一事务保存 Note + LearningEvent + projection_outbox
  -> ContextStore ingest/refresh
  -> 概念关系和记忆候选按独立策略投影
```

目标删除路径：

```text
校验 user_id 与删除权限
  -> 删除或标记规范笔记
  -> ContextStore.forget
  -> 清理 chunk、向量和缓存
  -> 删除/失效来源概念关系与未确认记忆候选
  -> 记录投影结果、重试和错误
```

硬约束：

1. 更新后不能继续召回旧版本内容。
2. 删除后不能从关键词、向量、缓存、图谱或记忆候选中召回残留内容。
3. 投影失败不能回滚已经成功保存的原始笔记，但必须可观察、可重试和可重建。
4. 每个索引和派生记录必须携带稳定来源、用户范围和版本。

## 6. 下一条实施切片与验收

下一条实现选择“聊天中的笔记检索”作为 `ContextStore` 首个真实业务流，暂不同时重写完整资料 RAG、时态记忆和概念图谱。

最低验收：

1. 笔记创建、更新和删除分别触发可重试的 `ingest/refresh/forget` 语义。
2. 聊天笔记检索只依赖 `ContextStore`，不再平行维护第二套检索入口。
3. 新增、更新、删除、重复投影和重建均有回归测试。
4. A 用户不能检索或加载 B 用户笔记。
5. 返回来源、命中片段、检索模式、索引/内容版本和降级状态。
6. 建立小型离线质量集，至少覆盖精确术语、同义表达、标题/标签、跨 chunk 上下文和无答案查询。
7. 无 embedding、投影失败或候选引擎不可用时，关键词降级不破坏聊天和笔记 CRUD。

本切片完成前，不启动 Qdrant 正式采纳、Graphiti 投影或 AgentRuntime 后台自学习；先证明数据边界、删除一致性和真实检索质量。

## 7. 非目标

- 本决策不要求立即部署三套数据库。
- 不把所有笔记自动转成长记忆。
- 不把用户在笔记中的自述自动当成已掌握证据。
- 不在本切片中实现 Obsidian 双向写回、Graphiti、Neo4j 或完整 Qdrant 迁移。
- 不为了“智能”绕过用户隔离、记忆审核、来源展示和删除语义。
