# 更新记录：用户画像原子 Upsert

## 本周期目标

- 修复用户首次生成画像时的并发插入竞争。
- 保持上一阶段已经建立的 flush-only 事务边界，不让画像服务重新取得提交权。

## 已完成

### 1. PostgreSQL / SQLite 原子写入

- `user_profiles.user_id` 继续作为稳定画像身份，不新增 schema 或迁移。
- 画像写入由“先查询、再插入/更新”改为数据库原生 `INSERT ... ON CONFLICT DO UPDATE`；两个请求同时首次计算同一用户画像时，不再依赖应用层时序来避开主键冲突。
- PostgreSQL 与 SQLite 使用相同的字段所有权清单；其他未声明方言保留显式兼容路径，不会被误标为已经具备原子竞争保证。

### 2. 字段所有权隔离

- 聚合计算只覆盖专注时长、学习天数、番茄钟、时段分布、薄弱点、近期表现和相应评分。
- `learning_style`、AI 评估、人格分析等由其他生产者维护的字段不进入冲突更新集合，重复刷新不会覆盖它们。
- Upsert 后重新读取当前事务内的 ORM 行，调用方得到数据库中的最终画像对象；服务仍只 flush，commit/rollback 继续由请求或 worker 入口负责。

## 数据与回滚

- 无 schema 变化、无需数据回填；已有画像在下一次刷新时自然进入新路径。
- 回滚代码只会恢复应用层“先查后写”，不会改变存量数据结构，但会重新暴露首次并发竞争，因此不建议单独回滚。

## 验证结果

- 画像事务与并发专项当前为 `7 passed`。
- 新增验证确认 SQLite 实际发出 `ON CONFLICT DO UPDATE`，且重复刷新后只有一条画像，并保留其他生产者拥有的字段。
- 本轮最终后端全量为 `497 passed, 10 skipped, 58 subtests passed`。

## 已知限制 / 后续事项

- 原子 upsert 解决同一主键的首次写竞争，不替代更高层的画像版本、来源时间和“较新计算不得被较旧计算覆盖”策略；出现真实乱序覆盖证据后应引入观察版本或条件更新。
- 下一模块建立服务事务所有权清单和静态架构守卫，防止新的领域服务静默增加 `commit()`。
